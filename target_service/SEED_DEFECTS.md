# 靶场缺陷清单（Ground Truth）

> 这份文件是**评测基准**，不是"我们发现了这些 bug"的宣传材料。
> 服务与缺陷都是人为构造的，缺陷为预埋，目的是让"用例质量"可以被量化。
> 类似 WebGoat / OWASP Juice Shop 的思路。

## 缺陷总表

| ID | 接口 | 缺陷类别 | 触发方式（一条用例） | 实际表现 | 期望表现 |
| --- | --- | --- | --- | --- | --- |
| D1 | `POST /api/v1/orders` | 文档与实现不一致 / 边界值 | `remark` 传 21~200 字符（文档允许 200） | 500（DB CHECK 失败） | 201，或接口层明确拒绝 |

## 对照组（行为正确，用于估算误报）

| 接口 | 正确行为 |
| --- | --- |
| `DELETE /api/v1/orders/{id}` 不带令牌 | 401 |
| `DELETE /api/v1/orders/{id}` 带正确令牌 | 200 |
| `DELETE /api/v1/orders/99999` 带令牌 | 404 |
| `POST /api/v1/orders` 缺 `item_id` | 422（Pydantic 拦截） |
| `GET /api/v1/orders/99999` | 404 |

对照组的作用：如果 AI 生成的用例对**正确行为**也报失败，说明用例本身有质量问题
（比如断言写错、错误地假设返回结构），这部分要算进**误报率**，
而不能当成"发现了新缺陷"。

## 与评测指标的关系

一次"用例 → 执行 → 缺陷"的完整链路里：

- **缺陷召回率** = 命中的 D 编号数 / 8
- **误报率** = 对对照组报失败的用例数 / 对照组用例数
- **重复命中** = 8 个缺陷总共被多少条用例命中（衡量用例是否冗余）

这三个数构成本项目最核心的一张表。

## 代码里的对应关系

| 本文件 | 代码 |
| --- | --- |
| 缺陷总表 | `app/executor/ground_truth.py` 的 `GROUND_TRUTH`（可执行的指纹：接口 + 失败类型 + 请求特征） |
| 对照组 | `cases/order_service_cases.json` 中 tag 含 `control` 的 C02 / C06 / C07 / C08 / C09 |
| 缺陷探针 | 同文件的 C10 ~ C18 |

**改靶场必须同步改这两处**，否则召回率会失真。`tests/test_triage.py` 里有一条测试
断言签名表恰好是 D1~D8 一条不多一条不少。

归因**不使用用例上的任何"预期缺陷"标签** —— 只依据观测信号（状态码、失败类型、请求特征）。
这样 M2 之后 AI 生成的用例（完全不带标签）也能走同一套评分逻辑。
