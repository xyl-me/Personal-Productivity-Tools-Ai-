# 接口用例智能生成与质量评测平台

从 **上传 Swagger** 到 **AI 生成用例** 再到 **质量评测** 和 **多格式导出** 的闭环工具。

这个项目要回答的核心问题不是"能不能用 AI 写用例"（那不稀奇），而是：

> **AI 生成的用例，凭什么说它是好用例？**

所以最重的三块不是生成，而是 **执行**、**归因** 与 **可量化**。没有 ground truth，
"降幻觉""提覆盖率"就都只是形容词。

## M0: 解析层的四个真实难点

1. **`$ref` 循环引用** —— `Node.children -> Node` 很常见。朴素递归会爆栈；解析时维护
   "正在展开的 ref 链"，成环时返回带 `x-circular-ref` 的占位 schema 截断，无环分支仍完整展开。
2. **`allOf` 的合并语义** —— 不拍扁，下游只拿到 `{"allOf":[...]}`，字段列表是空的。
   合并时**下界取 max、上界取 min**（`allOf` 是交集），`enum` 取交集，`required` 取并集。
3. **可空类型三种写法**（`nullable` / `anyOf: [X,null]` / `type:[X,"null"]`）统一折叠。
4. **`$ref` 字符串展开后无法恢复** —— 先用 `_deref_top()` 只解顶层引用、记下结构名
   （`CreateOrderRequest`），再全量展开。字段白名单和结构去重都靠这个名字。

## M1: 执行层与缺陷归因

- **用例断言"预期正确行为"**，不是"已知 bug"。实际返回 201 才算缺陷被测出来。
- **归因靠可观测信号**（接口 + 失败类型 + 请求特征），不靠用例标签 —— 否则召回率自证。
- **`ERROR` 与 `FAILED` 分开**：连不上/超时是环境问题，不进通过率、不进误报率。
- **串行执行 + 每条用例前重置数据**：被测接口有状态，并发会让失败无法复现。

| 失败类型 | 含义 | 典型缺陷 |
| --- | --- | --- |
| `server_error` | 5xx | DB 约束未在接口层校验 |
| `unexpected_success` | 期望 4xx，实际 2xx | 校验缺失、越权、状态机漏洞 |
| `status_mismatch` / `content_mismatch` | 码不对 / 内容不对 | 错误码用错、字段缺失 |
| `timeout` / `transport_error` | 请求没发成功 | 环境问题，单独统计 |

## M2: 生成引擎

### 输出契约的改动（相对原始方案）

原方案 `{"case_name":"", "params":{}, "expected":"", "type":"正向/异常"}` 有两处不可用：
`params` 混着 path/query/header/body 分不清位置；`expected` 是自由文本没法断言。改成：

```json
{"cases":[{
  "case_name":"...", "category":"boundary|positive|equivalence|error_guess|security",
  "type":"正向|异常", "scenario":"...",
  "request":{"path_params":{},"query":{},"headers":{},"body":{}},
  "expected":{"status":400,"note":"金额必须大于 0"}
}]}
```

### 四条降幻觉手段

1. 合法字段清单写进 Prompt（输入端压缩自由度）
2. `response_format=json_object` + `temperature=0.1`
3. 解析失败**带着错误信息**重试（模型能看到自己错在哪）
4. 字段白名单校验（逐条比对 `all_param_paths()`）

### 最反直觉的一条设计

> **校验只查"字段存不存在"，不查"值合不合法"。**

`amount=-1`、`page=0` 这些"非法值"本身就是要测的东西。若被校验层拒绝，异常用例全消失，
平台只剩正向用例。所以白名单的对象是**字段路径**，值原样放行交给被测服务判断。

### 并发与缓存

- 并发只用于 LLM 调用（`asyncio.Semaphore`）；退避重试只针对 429/超时，认证失败立即终止。
- 缓存键 = `sha256(model | temperature | prompt)`。把 prompt 放进键里：文档改一个字段
  prompt 就变，旧结果自动失效（只按接口路径缓存会在文档更新后返回过期用例）。
- **只在解析成功后写缓存**：否则一次被截断的响应会被永久缓存，之后每次重跑都回放坏数据，
  看起来像"模型每次都输出坏的"——这个坑真踩过一次，排查极费时。

### 真实模型跑出来的结果（DeepSeek，deepseek-chat）

第一次真跑（`--real`）暴露了三个问题，逐个修完之后指标翻倍：

| 指标 | 第一版 | 修复后 |
| --- | --- | --- |
| 产出用例 | 17 条（4 个接口 0 条） | **31 条（7 个接口全覆盖）** |
| 缺陷召回 | 2/8 = 25% | **4/8 = 50%** |
| 误报率 | 20% | **0%** |
| 未归因失败 | 2 条 | **0 条** |
| 幻觉/位置错配字段 | 12 | 32 |

三个问题都是**工程缺陷**，不是模型不行：

1. **没看 `finish_reason`** —— 4 个接口连续 3 次报 `Unterminated string`，其实是
   `finish_reason=length` 把 JSON 截断了；而我的重试策略把"截断"当"格式错"，
   用**同一个 prompt** 重发，必然在同一处再被截断，白烧 token。
   修法：检查 `finish_reason` → 截断时**条数减半**并换 prompt 再试。
2. **缓存了坏数据** —— 截断的响应被写进缓存，之后每次重跑都回放它。
   修法：只在 `parse_batch` 成功后才写缓存。
3. **让模型去猜外部事实** —— 模型不知道 `X-Admin-Token` 的值，也不知道哪个 `order_id`
   真实存在，于是"期望 200"的用例拿回 401/404，直接变成误报。
   修法：`data/runtime.json` 注入凭据与已知 ID（**值不进 Prompt**），
   并且按期望状态码区别对待：期望 401/403 的用例不带凭据，期望 2xx 的用例才覆盖真实 ID
   （否则"删不存在的订单→404"会被改成"删存在的订单→200"，反而制造误报）。

修完剩 4 个漏测（D1 备注超长、D2 负金额、D3 数量为 0、D4 SQL 注入）——**这次是模型真的没想到**，
不是工程问题。它老老实实写了正向和边界，但没做业务规则错误推测，这正好是 M3 规则分
"未覆盖标注场景"该扣分的地方。

## M3: 评测层

### 三路信号，权重从高到低

| 信号 | 内容 | 权重 |
| --- | --- | --- |
| 规则子分 | 12 条规则的加权覆盖（必测做门槛 + 加分微调）+ 用例质量 + 去重/密度惩罚 | 70% |
| 场景覆盖 | 人工标注的 31 条业务场景（机器可判定 matcher） | 报告项 |
| LLM 开放项 | 业务合理性、场景组合价值，必须给 case_id | 30% |

规则分两档：**必测**（正向、必填缺失、参数是否被用过、文档声明的边界、鉴权）与
**加分**（类型错误、枚举外值、注入、空串）。若连"类型错误"都算必测，
任何接口都会被压到 50 分以下，评分就没有区分度了。

### 三个"必须诚实"的设计

1. **没有 Key 时不编造模型分** —— 最终分等于规则分，并明说"已跳过评审"。
2. **低分不丢弃，进人工队列** —— 每条都带具体原因，丢掉会让人不知道自己漏了什么。
3. **一致性必须算出来** —— 只声称"我用 AI 打了质量分"没有意义，要说清和人工判断有多一致。

### 实测结果与诊断

```
规则分 vs 人工标注 (n=7)   ρ=0.685   MAE=13.31   κ=0.364
规则分 vs 场景覆盖分        ρ=0.559   MAE=18.12
```

**排序可信、阈值不可信。** 两个典型分歧：

| 分歧 | 规则分 | 人工分 | 根因 |
| --- | --- | --- | --- |
| `GET /api/v1/orders` | 92.5 | 62 | 文档没声明 `page ≥ 1`，规则认为"没有边界可测"就给了高分；人工按业务常识要求测上限 |
| `GET /admin/orders/export` | 33.4 | 60 | 规则重罚"一条用例、无正向"；人工认为管理接口首要场景是越权拒绝 |

**根因总结：规则是"文档立场"，人工标注是"业务立场"。** 这正是 LLM 评审该补的位置，
但前提是它能给出可核验的证据，而不是一个 80 分。

阈值扫描（κ）：60→0.125, 70→0.125, 75→0.364, 80→0.364, 85→−0.167, 90→0.000。
κ 随阈值大幅跳动说明 n=7 上任何"最优阈值"都是过拟合。**要可信结论，需要 3 名测试工程师
独立标注 30+ 接口后重算（Fleiss' κ）。这一步我没做，也不假装做了。**

### 用真实 AI 用例集做的一次指标校准

拿真跑出来的 31 条 AI 用例走同一套评测，结果**打脸**：

```
规则分:  AI 81.4  >  手写 65.1
缺陷召回: AI 4/8   <  手写 8/8
```

最刺眼的是 `POST /orders`：AI 场景覆盖只有 **2/7**（漏了金额负数、数量为 0、备注超长、
类型错误），规则分却 **85.7**，比手写的 5/7 → 70.7 还高。**规则分虚高，跨来源不可比。**

分两步定位、两步修：

| 假设 | 修改 | 结果 |
| --- | --- | --- |
| 规则集漏了"业务规则探测"：`amount`/`quantity` 文档没写 `minimum`，规则就看不见 | 新增必测规则 `business_rule_probe`（每个数值业务字段必须有 0/负值取值）+ 加分规则 `long_string_probe` | `POST` 倒挂 **+15.0 → +3.4** |
| 加分项（0.2 权重）在替"铺开浅用例"买单，抵消了必测缺失 | 改成门槛式：`coverage = 必测覆盖率 × (0.9 + 0.1 × 加分覆盖率)`，加分只能微调 ±10% | `POST` **+3.4 → −8.3**（方向修正） |

校准后逐接口对照（规则分 vs 场景覆盖，与手写基线比）：

| 接口 | AI 规则 | 手写规则 | AI 场景 | 手写场景 | 方向 |
| --- | --- | --- | --- | --- | --- |
| `POST /orders` | 71.2 | 79.5 | 2/7 | 5/7 | ✅ 修正 |
| `search` | 47.5 | 71.0 | 1/4 | 2/4 | ✅ |
| `admin/export` | 70.0 | 33.4 | 3/3 | 2/3 | ✅ |
| `GET /orders` | 100.0 | 92.5 | 4/5 | 3/5 | ✅ |
| `PUT status` | 94.2 | 32.0 | 3/4 | 1/4 | ✅ |
| `GET /orders/{id}` | 97.2 | 90.8 | 3/4 | 3/4 | — 持平 |
| `DELETE` | 95.3 | 90.8 | 3/3 | 3/3 | — 持平 |

**6/7 方向正确 + 1 持平。** 但跨来源 ρ 仍是 0.382（MAE 25.03 → 23.03），
手写基线对人工标注的 MAE 反而从 12.94 微升到 13.31。

结论（比"优化成功"更重要）：

> 规则分能回答**"两套用例谁更好"**（方向 6/7 正确），
> 不能回答**"这套用例有多少分"**（ρ、MAE 对不上，尺度不同）。
> 对外报质量必须三个数一起报：**规则分 / 场景召回 / 缺陷召回**，缺一个就会误导。

代价也说清楚：为了修跨来源可比性，牺牲了一点对单作者标注的拟合（MAE 12.94 → 13.31）。
我选择前者——单作者标注本身就有偏，而跨来源可比性是这套指标能不能用的前提。

## M4: 导出与界面

### 三个交付物

1. **`reports/*.xlsx`** —— 四张表：汇总 / 用例明细 / 质量评分 / 缺陷归因。
   表头冻结、列宽自适应、"需人工复核"的行标黄。
2. **`reports/test_*.py`** —— 可独立运行的 Pytest 脚本：只依赖 pytest + 标准库，
   内嵌用例数据，`BASE_URL` 环境变量指定被测服务。
3. **`reports/*.json`** —— 与平台内部同构的用例集，可再次导入。

### 三个设计决定

**1. xlsx 写成零依赖**
环境里既没有 openpyxl 也没有 xlsxwriter，而为了导出引入一个几 MB 的依赖不划算。
xlsx 本质是 zip + XML，需要的子集很小（内容类型 / workbook / styles / sheet），
于是直接按 OOXML 拼，字符串一律用 `inlineStr`。生成结果用 openpyxl 回读过（4 张表、
行列数、冻结窗格、样式色值都对）。

**2. 导出的脚本不复用平台代码**
交到别人机器上的脚本，多一层 `from app.xxx import` 就多一个跑不起来的理由，所以断言逻辑
在模板里原样写死。但"逻辑一样"不能靠自觉 —— 用两组用例分别跑平台与脚本、
比对失败集合来证明（见上面的 M4 结论）。

**3. 重置必须走 HTTP（这条踩过坑）**
最初导出的脚本用 `CASE_RESET=target_service.main:reset_demo_data` 在本进程里重置。
结果脚本在子进程里 import 被测应用，创建的是**它自己那份内存数据库**，
对服务端的数据库毫无影响 —— 于是所有依赖数据条数的用例全部莫名失败，且报错信息毫无线索。
改成：靶场提供一个 `POST /internal/reset`（`include_in_schema=False`，不出现在对外文档里），
脚本在每条用例前 HTTP 调一次。

### 关于界面

界面逻辑全部放在 `app/pipeline.py`，Streamlit 只负责收参数/展示/下载 ——
界面是最难自动化测试的一层，逻辑留在回调里就再也测不了了。
本环境没装 streamlit，所以界面**只验证了可导入与结构完整**，没有做人肉点击验证。

## M5: 规模验证与性能

只有 7 个接口的靶场证明不了"能处理真实规模的文档"。`benchmarks/synthetic.py` 造了一份
**400 接口 / 201 KB** 的文档，刻意还原真实文档的两个特征：

- **组件被反复引用**：所有列表接口共用 `PageMeta` 信封，每个接口 body 引用各自的 Model；
- **引用链很深**：`Model39 → Model38 → … → Model0`，展开一个深层模型会连带展开整条链。

`python benchmarks/run_bench.py` 给出"缓存开/关"的 A/B（同一进程内对比，避免跨次运行抖动）：

| 接口数 | 文档 | 整体解析 无/有(ms) | 提速 | $ref 展开 无/有(ms) | 缓存命中 |
| --- | --- | --- | --- | --- | --- |
| 50 | 42 KB | 26 / 24 | 1.1x | 9 / 4 | 66 |
| 101 | 65 KB | 49 / 29 | 1.7x | 34 / 15 | 134 |
| 200 | 110 KB | 103 / 77 | 1.3x | 101 / 27 | 293 |
| 401 | 201 KB | 287 / 159 | 1.8x | 205 / 23 | 628 |

另有：Prompt 构建 150ms / 103 万字符（平均 2,576 字符/接口）；
生成调度（零延迟模型、并发 8）401 接口 228ms ≈ **1,762 接口/秒**。

### 优化本身值得说，但"只快了 1.8 倍"更值得说

第一版解析器没有任何缓存：同一个 `$ref` 在 200 个接口里被展开 200 次，每次都要重新递归整条链。

加缓存之后 **`$ref` 展开快了 9~13 倍（205ms → 23ms）**，但**整体解析只快了 1.8 倍** ——
因为 Amdahl 定律：展开只占一部分时间，剩下的 `normalize_schema`（每个 media type 都要
递归重建整棵 schema 树）变成了新瓶颈，它占总耗时的 80% 以上。

这条结论比"优化了 10 倍"有用得多：**瓶颈已经从展开层转移到规范化层**，
下一步应该按 `$ref` 记忆化 normalize 的结果，而不是继续在展开层抠。

### 三个必须守住的不变量

优化最容易引入的是"看起来更快、结果悄悄变了"的 bug，所以三条都有测试：

1. **缓存不能改变结果** —— 同一文档解析两次，`model_dump()` 必须完全相等；
2. **循环引用仍然被识别** —— 缓存键是 `$ref` 字符串，但"是否处于引用链中"必须看展开栈，
   所以缓存**只在栈为空时生效**（栈非空时同一组件可能被截断成 `x-circular-ref`）；
3. **不同接口不能共享可变对象** —— 缓存让多个接口拿到同一个展开结果，
   于是 `normalize` 层必须复制 `enum` / `required` 这类列表，否则"改 A 接口的约束，B 接口跟着变"。

顺带一个被否掉的方案：给缓存返回 `deepcopy` 以保证隔离。实测 deepcopy 一份 40 层嵌套 schema
要 415ms，比不缓存（205ms）还慢 —— 所以只能选择"共享 + 只读约定 + normalize 层做浅复制"。

## M6: 文档 diff 与增量生成

原始痛点是"接口文档更新频繁，人工用例跟不上"。前面的 M0~M5 解决了"有没有"，
这一层解决"每次迭代花多少钱"——真实迭代一次只动几个接口，全量跑等于浪费 80% 以上。

### 只比 URL 列表是不够的

`fixtures/specs/orders_v1.json` / `orders_v2.json` 模拟了一次典型迭代：
加字段、收紧约束、删接口、加接口。

```
两版共涉及 8 个接口: 新增 1, 删除 1, 变更 2, 未变 4; 需重新生成 3 个 (节省 62%)

| 接口 | 状态 | 变更点 | 严重性 |
| PATCH /api/v1/orders/{order_id}/remark | 新增 | 新接口 | - |
| GET /api/v1/orders/search | 删除 | 调用方需确认下线 | breaking |
| GET /api/v1/orders | 变更 | query.page_size maximum 变化 None -> 50 | breaking |
| POST /api/v1/orders | 变更 | body.channel 新增字段; body.quantity minimum None -> 1; body.remark maxLength 200 -> 120 | breaking |
```

关键在最后两行：**接口清单没变，但约束收紧了**。这类变更不改变 URL 列表，却能让旧用例全部失效——
只比路径的实现会把它们判成"未变更"而跳过，这是最危险的一种漏测。

所以做的是**字段级 diff**：参数与 body 字段逐个比对 `required / type / enum / minimum /
maximum / minLength / maxLength / nullable`，并区分方向：

- **breaking**（删除字段、改必填、枚举收窄、上限收紧）：旧用例会挂，必须回归
- **relaxed**（新增可选字段、改非必填、枚举变宽）：旧用例仍通过，只需补新场景

### 实测：3 个接口、54% 成本、100% 变更点覆盖

```
全量 | 7 个接口 | Prompt 10,769 字符 | 100%
增量 | 3 个接口 | Prompt  4,960 字符 |  46%

真实增量生成: 3 次调用 / 18 条用例 / prompt 2842 + completion 1705 tokens
变更点覆盖: 5/5 = 100%
```

### 增量生成最大的风险不是"少生成"，是"生成了却没测到变更"

`app/evaluator/changes.py` 做字段级核对：把 diff 里的每个变更点拿出来，
看该接口的用例里有没有一条真的给这个字段赋过值。没覆盖的直接列出来并标注 breaking 数量——
这是增量生成的质量门禁，而不是"看起来跑完了"。

**诚实边界**：这里是"触到"，不是"测对"。比如 `remark` 上限从 200 降到 120，
用例只要写到 `remark` 就算覆盖，但有没有正好测 121 字符的边界，得靠 M3 的规则分与人工看。

另外两个刻意的决定：

- **删除的接口不生成用例**，只报告。写一条"应该 404"的用例没意义——它已经不该存在了，
  真正该做的是在网关/监控侧确认调用方下线了。
- **增量用例打 `incremental` / `changed` / `breaking` 标签**，报告里能一眼看出
  "这条是因为文档变更才生成的"，也方便后续只回归这批。

## 已知局限

- **生成环节的质量数字来自手写 fixtures**，不代表 DeepSeek 的真实水平；配 Key 跑 `--real` 才有意义。
- **一致性数字来自单作者种子标注**（n=7），且标注与规则共享同一套 rubric，κ 偏乐观。
- **靶场的 8 个缺陷是刻意设计的**，覆盖面（注入、越权、边界、类型、状态机）虽真实但不全面。
- **Streamlit 界面未做交互验证**（环境未安装）。
- **性能数字有 ±20% 的机器抖动**，所以基准表里同一进程做 A/B，并且只看数量级与相对倍速。
