# 标注说明（RUBRIC）

这份文档是 `quality.json` 里人工打分的依据。写下来的目的有两个：

1. **可复现** —— 换个人按同一份 rubric 标注，结果应该接近；
2. **可质疑** —— 分数背后的假设是公开的，可以逐条检视。

## 打分维度

人工分评价的是**这套用例对一个接口的覆盖质量**，不是"跑通率"，也不是"发现了几个 bug"。
后者由执行层单独统计，混在一起会让两个指标互相污染。

| 分数段 | 含义 |
| --- | --- |
| 90-100 | 正向 + 全部声明的边界 + 鉴权/异常维度齐全，几乎无可补充 |
| 75-89 | 正向 + 主要异常维度，缺 1 个次要场景 |
| 60-74 | 正向 + 少量异常，缺 1~2 个较重要的场景 |
| 40-59 | 有正向但异常维度明显不足，或有异常但缺正向 |
| 20-39 | 只有单一维度（通常只有一条用例） |
| 0-19 | 用例不可用：无预期状态码、参数全被剔除、内容重复 |

`human_pass` 的阈值与系统一致：**80 分**。

## 与规则分的区别

- **规则分**看的是通用维度（有没有必填缺失、有没有长度边界、有没有鉴权断言），
  维度清单由 `app/evaluator/rules.py` 从文档自动推断适用性；
- **人工分**看的是**这个接口的业务场景**（"备注取 21~200 字符"、"令牌错误应 401"），
  清单在 `scenarios.json`，只能人写。

两者不一致是正常的，而且不一致的地方最有价值 —— 它暴露了规则模型的盲区。
`scripts/run_m3.py` 会把这些分歧逐条列出来。

## 已知局限（必须主动说明）

- 标注由**一个人**完成，且这个人同时设计了规则 → κ 偏乐观；
- 样本量只有 7 个接口，统计意义有限；
- 要得到可信的一致性数字，需要 3 名测试工程师**独立标注**同一批输出，再算 Fleiss' κ。

当前这套数据的作用是**验证一致性计算的管线**，而不是给出"评分准确率 90%"这种结论。
